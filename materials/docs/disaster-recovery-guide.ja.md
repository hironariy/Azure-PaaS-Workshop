# BCDR ガイド（事業継続と災害復旧）

このガイドでは、ワークショップの PaaS アーキテクチャにおける **事業継続（Business Continuity）/ 災害復旧（Disaster Recovery）= BCDR** の設計方針と運用ランブックの考え方を解説します。

> **演習手順について:** Cloud Shell から順番に実行する Day 2 の復旧演習は [Day 2: 信頼性と復旧](learner/day-2-reliability.ja.html) を参照してください。このページは本番環境を見据えた BCDR 設計のリファレンスです。

- **フロントエンド**: Azure Static Web Apps (`Standard`)
- **バックエンド**: Azure App Service（Linux, Node.js 22 LTS）
- **データベース**: Azure Cosmos DB for MongoDB vCore
- **シークレット**: Azure Key Vault
- **監視**: Application Insights + Log Analytics

> **ワークショップ標準構成の前提:**
> 演習でデプロイする標準構成（`B1` / `M25` / `HA=false` / 単一リージョン）は学習用にコストを抑えた構成であり、デプロイスロット、ゾーン冗長、DB の自動フェイルオーバー（HA）、セカンダリリージョンは含まれていません。Day 2 の演習では **App Service の再起動・同一ソースからの再デプロイ・既知コミットへのロールバック・DB データの永続性確認** を実施します。

---

## 1. 継続性目標（RPO / RTO）の定義

システム設計時には、ビジネス要件に基づいて次の 2 つの目標値を定義します。

- **RPO（Recovery Point Objective：目標復旧時点）**: 障害発生時に許容できるデータ損失の最大時間幅（例: 直近 15 分以内のデータまで復元する）
- **RTO（Recovery Time Objective：目標復旧時間）**: 障害発生からサービスを再開するまでに許容できる最大停止時間（例: 1 時間以内に復旧する）

## 2. 想定する障害シナリオと対策

### 2.1 コンポーネント単位の障害（日常的な運用で最も多いケース）
- **想定事象**: App Service プロセスの応答不良、デプロイ後のアプリケーション不具合、設定ミス
- **主な対策**:
  - ヘルスチェック（`/health`, `/api/health`）と Application Insights による早期検知
  - App Service の再起動（`az webapp restart`）
  - 正常動作を確認済みの Git コミット（SHA）からの再ビルド・再デプロイ（本番環境ではデプロイスロットのスワップ戻し）

### 2.2 リージョン規模の障害（低頻度・高影響）
- **想定事象**: プライマリリージョン全体の大規模障害
- **主な対策（本番拡張構成）**:
  - セカンダリリージョン用のパラメータファイルとリソースグループを用意し、Bicep でインフラを再展開できるようにする
  - Cosmos DB のバックアップ復元またはマルチリージョン構成と、カスタムドメイン / Front Door の切り替え手順（Runbook）を整備する

## 3. サービス別の BCDR 設計方針

### 3.1 Static Web Apps（フロントエンド）
- **基本原則**: ステートレスであり、Git リポジトリのソースコードと設定値からいつでも再構築できます。
- **本番設計のポイント**: セカンダリ環境に展開する際は、新しい Static Web Apps のホスト名を Entra ID フロントエンドアプリの SPA リダイレクト URI に追加し、Linked Backend の接続先もセカンダリの App Service に向けます。

### 3.2 App Service（バックエンド）
- **基本原則**: ステートレスな実行環境であり、Bicep テンプレートとビルド成果物（ZIP）から再現できます。
- **本番設計のポイント**: 本番環境では `Premium v3` プラン以上を選択して複数インスタンス・ゾーン冗長を有効化し、ステージングスロットで `/health` を確認してからスワップする運用を推奨します。

### 3.3 Cosmos DB for MongoDB vCore（データベース）
- **基本原則**: ステートフルなデータ層であり、RPO を左右する最重要コンポーネントです。
- **本番設計のポイント**:
  - 本番ワークロードでは `M30` 以上のクラスター層を選択し、ゾーン内高可用性（HA）を有効化します（※ `M30` 以上から `M25` へのダウングレードはできません）。
  - バックアップ保持期間とポイントインタイムリストア（PITR）の手順を事前に検証しておきます。

### 3.4 Key Vault（シークレット）
- **基本原則**: 接続文字列などのシークレットと RBAC ロール割り当てを Bicep で一貫して管理し、App Service のマネージド ID から Key Vault 参照で取得できるようにします。

## 4. リージョン切り替えランブックの構成例（本番向け参考）

本番システムでセカンダリリージョンへの切り替え手順書を作成する際は、次の 4 フェーズで整理すると運用しやすくなります。

1. **フェーズ A（平常時の準備）**: Bicep テンプレート・パラメータの維持、デプロイスクリプトの定期検証、バックアップ復元テストの実施。
2. **フェーズ B（インシデント判断）**: コンポーネント単位の障害かリージョン障害かを切り分け、リージョン切り替えの実施を宣言。
3. **フェーズ C（復旧作業の実行）**: セカンダリリージョンへの Bicep デプロイ、DB の復元、バックエンド・フロントエンドのデプロイ、Entra ID リダイレクト URI の更新、エンドポイントの切り替え。
4. **フェーズ D（切り替え後の検証）**: `/health` と `/api/health` の応答、MSAL サインイン、記事の作成・閲覧・更新・削除、および Application Insights へのテレメトリ流入を確認。
